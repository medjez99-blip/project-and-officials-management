 0. CONTEXT & DECISIONS (locked in — do not re-litigate unless something breaks)
================================================================================

 Project type .......... Personal project, targeting a small limited group.
                          Not a public production system (yet).
 Data sensitivity ...... Modest. May add a policy file (privacy/terms) later.
                          No compliance driver to solve for today.
 Hosting intent ........ Supabase managed (not self-hosted) — unless data-
                          residency concern appears later.
 Offline behaviour ..... Local-first + sync. Writes land in IndexedDB first;
                          background push to Supabase. Network loss must not
                          lose user data.
 Admin user creation ... Via a Supabase Edge Function calling admin.createUser.
                          Keeps current UX: admin types name + email + password.
                          No public signup form.
 Existing users ........ Force a password reset for everyone on cutover.
                          Current SHA-256/cyrb53 hashes cannot be imported.

 Out of scope (today):
   • Self-hosting Supabase
   • Multi-tenancy
   • SSO / OAuth providers

 PHASE 4 — Local-first data layer   (≈1–2 days — the biggest phase)
────────────────────────────────────────────────────────────────────────────────

 Architecture principle:
   IndexedDB (or localStorage) = SOURCE OF TRUTH for the client.
   Supabase           = SYNC TARGET + multi-device bridge.
   The UI never blocks on a network call.

 Steps, in order — each is a shippable slice:

 [ ] 4a. Add a sync-queue table (IndexedDB) — one row per pending write:
         { id, entity: 'project'|'visit'|'photo', op: 'upsert'|'delete',
           payload, projectId, createdAt, retries }.
 [ ] 4b. Every write to `projects` in local state must also enqueue a
         sync-queue row. `save()` becomes `saveLocally() + enqueue()`.
 [ ] 4c. Background flusher:
         - On app start, on network online event, on a 30s timer:
           drain the queue in order; on failure, retry with backoff.
         - On success, remove the queue row.
 [ ] 4d. Pull on start / on login / on window focus:
         - Fetch remote projects where updated_at > lastSyncTime.
         - Merge: newest `updatedAt` wins per project. Do not overwrite
           a locally-modified row that has a pending sync-queue entry.
 [ ] 4e. Conflict strategy (simple, sufficient for this app):
         - Same project edited on two devices → last-write-wins by
           `updatedAt`. Acceptable because a single user rarely edits
           the same project from two devices simultaneously.
         - Do NOT implement real merge for now. Note it in §6 open questions.
 [ ] 4f. Status indicator in the topbar: "Synced", "N pending", "Offline".
         Small badge next to the user chip. Serves as diagnostic.

 Gate: turn off WiFi → create a project → turn WiFi on → project appears in
       Supabase within 30s. No data loss.

 PHASE 5 — Admin user creation (Edge Function)   (≈2–4 h)
────────────────────────────────────────────────────────────────────────────────

 Why an Edge Function: admin.createUser requires the service_role key, which
 MUST NOT live in browser code. The function runs server-side with that key,
 but only after verifying the caller is an admin.

 [ ] Create a Deno Edge Function `create-user`:
       - Reads the caller's JWT from the Authorization header.
       - Looks up the caller's role in `profiles`.
       - If not 'admin' → 403.
       - Else → calls admin.createUser(name, email, password).
       - Optionally sets role = 'admin' if requested.
       - Returns the created user's id.
 [ ] Deploy it: `supabase functions deploy create-user`.
 [ ] Update the "new user" form in the Users modal to call the function
     instead of createUser().
 [ ] Add a parallel `reset-password` function (admin-only) that calls
     admin.updateUserById({ password }).
 [ ] Error handling: show the function's error message in #nuErr / #pwErr.

 Gate: sign in as a non-admin, try to call the function via DevTools console →
       403. Sign in as admin → 200 and the user exists.

 2. TABLE SCHEMA STRATEGY  — how to keep columns easy to add/remove
================================================================================

 Requirement: I want to add or drop fields on a project (e.g. new field
 "budget", "contact_email2", "risk_level") WITHOUT writing SQL every time.

 Answer: store the whole project as a single `data jsonb` column.

 projects table:
   id          uuid     PK, generated
   owner_id    uuid     → auth.users.id
   name        text     (denormalized from data.name, for sorting/searching)
   data        jsonb    (the WHOLE project object — every field lives here)
   updated_at  timestamptz  (for sync delta)

 Consequences:
   + Adding a field = a UI change only. No ALTER TABLE.
   + Matches the current JS object shape exactly — no mapper layer.
   + Restoring a backup = insert one row per project.
   - Filtering/searching on a specific field is slow unless you add a
     generated column or an index.
     → For this app: all filtering happens client-side already. Fine.
   - No per-field type checking at the DB level.
     → Client-side validation covers it.

 Rule of thumb:
   Stay in `data jsonb`  →  anything the UI shows or edits.
   Promote to a real column → only when:
     • It must be enforced by an RLS policy (e.g. owner_id), OR
     • It is queried on every page load and needs an index
       (e.g. name if the list gets huge).

 profiles table (DO NOT make this jsonb — role must be RLS-checkable):
   id          uuid     PK → auth.users.id
   name        text
   email       text     (denormalized, read-only)
   role        text     CHECK (role IN ('admin','user'))
   created_at  timestamptz

 visit-photos bucket:
   Path convention: {project_id}/{photo_id}.jpg
   → Easy to bulk-delete all photos of a project.

 3. THINGS TO CONSIDER  (not scheduled — decide when relevant)
================================================================================

 [?] Data residency:
       Personal project, small group → Supabase managed in the closest region
       is fine today. If a policy file (privacy / terms) is added later and
       mentions "data stays in country X", revisit: either self-host Supabase
       (Docker) or migrate to a managed service with a local region.
       Add this as a line item in the policy file when written.

 [?] Cost:
       Free tier: 500 MB DB, 1 GB storage, 50k MAU. This app uses a fraction.
       Watch: storage grows with photos. At 1 GB, photos cap out — plan an
       "export and delete old visits" feature (see §4 data extraction).

 [?] Backups:
       Free tier = 7-day retention. Add a manual "export JSON" habit
       (already in the app) once a month. Or schedule a GitHub Action that
       hits the Supabase REST API and commits a JSON snapshot.

 [?] Offline completeness:
       Local-first + sync means some features will lag until online:
         - User list (roster) — cache last fetched, show "offline — stale".
         - Signed photo URLs expire after 1h — cache blobs locally, do not
           rely on the URL for offline display.
       Define acceptable staleness per feature. Document it.

 [?] Delete semantics:
       Hard delete everywhere (current behaviour) or soft delete (deleted_at
       column)? Soft delete = recoverable + syncable. Hard delete = simpler.
       For small group, hard delete is fine — but add a "trash" period later
       if users ask.

 [?] Photo storage growth:
       Each stamped photo ≈ 200–400 KB. 50 visits × 5 photos ≈ 60 MB.
       Free tier 1 GB → ~80 projects with full visit history. Fine for now.

 [?] Session refresh:
       Supabase tokens expire. supabase-js auto-refreshes — but ensure
       onAuthStateChange keeps currentUser in sync. Otherwise a stale role
       cache could leak admin buttons.

 [?] Deno Edge Function cold start:
       First invocation after inactivity takes ~1s. Fine for admin actions
       (rare). If it becomes annoying, add a warm-up ping on app load.

 [?] Service worker cache vs Supabase:
       sw.js already bypasses supabase.co — keep that rule. Do not add
       Supabase API responses to the shell cache; the app's own
       local-first layer handles offline.

================================================================================
 5. RISKS / OPEN QUESTIONS
================================================================================

 [!] "owner" definition mismatch.
     Currently `isOwner()` matches by email OR responsible-name. With
     Supabase, ownership should be a real FK (owner_id → auth.users.id).
     Decide: does a project get reassigned when "responsible" changes in
     the UI? Or is owner_id separate from responsible? → Answer before
     Phase 4.

 [!] Conflict strategy simplicity.
     Last-write-wins is fine until two people edit the same project
     simultaneously. If that becomes common, need per-field merge. Not
     today.

 [?] Edge Function cold start + region.
     Deploy the function in the same region as the DB. Otherwise +200 ms
     latency per admin action.

 [?] Admin editing their own password via the reset-password function.
     Works, but the current UI hides the reset button on self. Decide:
     allow or not. (Recommendation: allow — it's a common UX expectation.)

 [?] What happens when the service worker updates while a user is mid-session?
     Currently: skipWaiting() + clients.claim() = silent takeover.
     If a user is filling a form during the takeover, nothing is lost
     (state is in DOM), but a mid-upload photo could be interrupted.
     Acceptable for now. Consider "update available" toast in a later pass.

 [?] Storage cleanup on project delete.
     Deleting a project must delete its photos from Storage too, or the
     bucket grows. Do it in an Edge Function (server-side, RLS-safe).

 [?] Photo signed URLs expiring.
     A cached HTML page showing a photo URL that expired = broken image.
     Mitigation: always fetch blobs to IndexedDB and render from blob URLs
     (already what the current lightbox does). Keep that behaviour.
