 2. TABLE SCHEMA (as deployed)
================================================================================

 projects table:
   id          text PK               ← NOT uuid (matches app's uid() format)
   owner_id    uuid → auth.users.id (ON DELETE CASCADE)
   name        text                  (denormalized for sorting)
   data        jsonb                 (full project object — every field lives here)
   updated_at  timestamptz           (auto-updated by trigger)

 profiles table (NOT jsonb — role must be RLS-checkable):
   id          uuid PK → auth.users.id (ON DELETE CASCADE)
   name        text
   email       text                  (denormalized)
   role        text CHECK IN ('admin','user')
   created_at  timestamptz

 visit-photos bucket:
   Path convention: {project_id}/{photo_id}.jpg
   → Easy to bulk-delete all photos of a project.
   → Path prefix is used by storage RLS policy to verify project ownership.

 Rule of thumb:
   Stay in `data jsonb` → anything the UI shows or edits.
   Promote to a real column → only when:
     • It must be enforced by an RLS policy (owner_id), OR
     • It is queried on every page load and needs an index.

       later mentions "data stays in country X", revisit hosting location.

 [?] Cost:

       Watch: storage grows with photos. Each stamped photo ≈ 200–400 KB.
       At 1 GB → ~2500 photos cap. Plan "export and delete old visits" if needed.

 [?] Backups:
       Free tier = 7-day retention. Manual export via app UI is still available.
       Consider a GitHub Action hitting Supabase REST API monthly for archival.

 [?] Offline completeness:
       ✓ Projects: fully offline.
       ✓ Photos (recent): available via local IndexedDB.
       ✗ Photos (fresh device): require network for signed URL.
       ✗ User roster: cached from last fetch, refresh on focus.

 [?] Delete semantics:
       Hard delete everywhere. Tombstones in localStorage ensure the delete
       reaches Supabase eventually. No soft-delete / trash period.

 [?] Session refresh:
       Supabase-js auto-refreshes tokens. onAuthStateChange keeps currentUser
       in sync. No manual session handling needed.

 [?] Service worker vs Supabase:
       sw.js bypasses supabase.co — API responses are not cached.
       The app's local-first layer handles offline state for those.

 5. RISKS / OPEN QUESTIONS (all resolved unless noted)
================================================================================

 [x] "owner" definition — RESOLVED.
     Ownership = owner_id in projects table.
     resolveOwnerId() maps: project.email → profiles.email, then
     project.responsible → profiles.name, then fallback currentUser.id.
     Reassignment happens naturally when the email field changes in the UI.

 [x] Conflict strategy — RESOLVED.
     Last-write-wins by updatedAt. Acceptable because a single user rarely
     edits the same project from two devices simultaneously.

 [?] Edge Function cold start + region — MONITOR.
     First invocation after inactivity takes ~1s. Fine for admin actions (rare).
     Deploy the function in the same region as the DB.

 [?] Admin editing their own password via reset-password.
     Currently the UI hides the reset button on self. Decide: allow or not.
     (Recommendation: allow — it's a common UX expectation.)

 [?] Service worker updates mid-session.
     skipWaiting() + clients.claim() = silent takeover. Form state is preserved
     (in DOM), but a mid-upload photo could be interrupted. Acceptable.

 [x] Storage cleanup on project delete — RESOLVED.
     Enqueued photo-deletes BEFORE project removal, so RLS on the still-
     existing project row allows the delete.

 [x] Photo signed URLs expiring — RESOLVED.
     Local blob URLs are preferred. Signed URLs only used as fallback for
     fresh devices; expiry (1h) is longer than any typical session refresh.

 [x] Queued writes blocking the entire queue — RESOLVED.
     flushQueue() drops permanent failures (RLS/permission/not-found/invalid)
     and continues. Only transient errors (network) break the loop for retry.

 [x] Tombstone resurrection — RESOLVED.
     markDeletedLocally() is synchronous (localStorage). Even a mid-reload
     delete leaves a tombstone. pullFromSupabase honors tombstones.
